# TicketFlow 网关压测报告

测量日期为 2026-11-22。压测客户端运行在 Windows 11 宿主机，服务运行在同机 Docker Desktop Linux 引擎。引擎 29.4.0，分配 24 个逻辑 CPU、约 15.5 GiB 内存。PostgreSQL 17.12、Redis 8.10.2、Python 3.14.7、Locust 2.47.0。独立 Compose 项目 `ticketflow-load` 以 Nginx 网关 `http://127.0.0.1:18080` 为唯一压测入口，DRF 和 FastAPI 各运行一个 Web worker。

## 数据与口径

- 专用卷中生成 5,000 张账户类工单，其中 4,000 张处理中、1,000 张待处理，四档优先级各 1,250 张。固定 UUID 的详情样本包含 3 条日志和 8 条回复。标准演示种子另外提供知识库和基础账号。
- DRF 各组均使用同一客服账号 `tf_agent`。列表固定 `q=TicketFlow load fixture&size=20`，看板使用相同的 `q`，详情固定为工单 `e850429a-0b47-58c0-8e82-c9f308fc2c9c`。N+1 档在压测进程内取消工单关联 JOIN 和时间线预取，将时间线关联的操作人、回复人交给 ORM 延迟加载。两档走相同的路由、权限、过滤和序列化。
- 看板冷组为每次查询分配新的 Redis 看板键，执行正常的 Redis 查找、数据库聚合和带 TTL 回写。热组压测前预热同一个键。两组的 Redis 读结果由 `X-Load-Dashboard` 逐请求核对。SQL 数使用视图内 `execute_wrapper` 采集，范围为视图动作。
- AI 使用 Mock 正常模式，分析延迟 350 ms，流式第一段延迟 350 ms、后续每段 180 ms，共 8 段。上游并发槽位 4 个，排队上限 1 秒。分析使用不重复的工单文本和未命中的分析缓存，SSE 固定同一工单。各 AI 组分开使用专用客服账号，保留登录和 AI 上下文限流。
- 同组所有虚拟用户登录并完成预热后开始采样，每个用户只登录一次并复用 token。冷、热看板各设 15 秒运行时限，其余各组为 20 秒，均含启动和登录。退出时最多等待 5 秒结束在途请求。吞吐和失败率取 HTTP 行，首字取首个非空 `delta`，完成时间取收到 `done` 的成功流。排队时间由 FastAPI 在信号量获取处用单调时钟记录，包含等待超时的尝试。
- 周期 CSV 用于查看采样过程。表格取停止后由 Locust 同一统计对象导出的 `*_final_stats.csv`，纳入最后结束的请求。原始 CSV 见 [压测结果目录](../../tests/load/results/)。

## DRF 工单

| 场景 | 用户数 | 请求数 | RPS | 错误率 | P50 (ms) | P95 (ms) | P99 (ms) |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 列表 N+1 | 8 | 322 | 16.44 | 0% | 480 | 590 | 650 |
| 列表优化 | 8 | 730 | 37.24 | 0% | 210 | 310 | 370 |
| 详情 N+1 | 8 | 630 | 32.24 | 0% | 240 | 300 | 410 |
| 详情优化 | 8 | 740 | 37.86 | 0% | 210 | 260 | 370 |
| 看板冷缓存 | 8 | 698 | 48.01 | 0% | 160 | 200 | 290 |
| 看板热缓存 | 8 | 920 | 64.02 | 0% | 120 | 150 | 230 |

列表优化组的吞吐约为基线的 2.27 倍，P95 从 590 ms 降到 310 ms。详情吞吐提高约 17%，P95 从 300 ms 降到 260 ms。最终提交的 SQL 探针在预热后测得列表从 62 条降到 6 条，详情从 26 条降到 12 条。连续两次采集的列表和详情结果相同。看板冷档两次采集共观测到 10–12 条 SQL，CSV 保留第二次的 10、11 条。热缓存命中时为 5 条，两档的响应数据摘要一致。最终压测窗口内，热缓存吞吐比冷缓存高约 33%，P95 低 50 ms。[SQL 探针 CSV](../../tests/load/results/query-probes.csv)

首轮 20 秒热组中，1,226 次请求有 2 次未通过数据或缓存路径的合并断言。最终运行分别校验两者，并用相同的 15 秒窗口采集冷、热组。

## FastAPI Mock

| 场景 | 用户数 | HTTP 尝试 | 成功 RPS | HTTP 错误率 | 请求 P50 / P95 / P99 (ms) | 排队 P50 / P95 / P99 (ms) |
| --- | ---: | ---: | ---: | ---: | --- | --- |
| 分析，低于槽位数 | 2 | 103 | 5.17 | 0% | 380 / 400 / 420 | 0 / 0 / 0 |
| 分析，高于槽位数 | 12 | 224 | 11.25 | 0% | 1,100 / 1,100 / 1,400 | 670 / 680 / 680 |
| SSE，低于槽位数 | 2 | 24 | 1.19 | 0% | 1,700 / 1,900 / 1,900 | 0 / 0 / 0 |
| SSE，高于槽位数 | 12 | 162 | 2.30 | 69.75% (113/162) | 1,100 / 2,500 / 2,700 | 1,000 / 1,000 / 1,000 |

SSE 请求时间一栏包含建流前的 HTTP 错误。以下延迟只取成功流，排队显示为 0 表示低于 Locust 的毫秒分桶精度。

| 用户数 | 成功流 | 首字 P50 / P95 / P99 (ms) | 完成 P50 / P95 / P99 (ms) |
| ---: | ---: | --- | --- |
| 2 | 24 | 380 / 410 / 410 | 1,700 / 1,900 / 1,900 |
| 12 | 49 | 890 / 1,400 / 1,400 | 2,200 / 2,700 / 2,700 |

同一分析 Mock 延迟下，12 用户把吞吐从 5.17 拉到 11.25 RPS，排队 P95 增加到 680 ms。12 用户流式组的槽位占用时间更长，113 次失败均为建流前的 `503 UPSTREAM_BUSY`，49 个成功流均收到首个 `delta` 和 `done`。

断开探针在四路 SSE 已各自收到首个 `delta` 时读到 4 个槽位全部占用。客户端主动关闭连接后，11.149 ms 内的首次采样已看到 4 个槽位全部恢复、等待数为 0，随后网关健康探针返回 HTTP 200 和 `{"status":"ok","redis":"ok"}`。[断开探针 CSV](../../tests/load/results/disconnect.csv)

结论适用于同机网关、单进程、短窗口和固定 Mock 延迟。真实模型提供方和长时生产流量仍待测量。

## 复现命令

以下命令从仓库根目录在 PowerShell 执行。准备脚本会在 Git 忽略的 `backend-drf/tmp/ticketflow-load/` 下生成隔离栈配置和本地凭据，重复运行沿用已有配置。数据脚本生成固定的工单 ID 与数据分布。

```powershell
$env:Path = 'C:\Program Files\Docker\Docker\resources\bin;' + $env:Path
$env:PYTHONUTF8 = '1'
uv sync --project tests --locked --group load
python tests/load/prepare.py
$work = 'backend-drf/tmp/ticketflow-load'
$compose = @('compose', '-p', 'ticketflow-load', '-f', 'deploy/docker-compose.yml',
             '-f', 'tests/load/compose.yml', '--env-file', "$work/.env")
docker @compose up -d --build --wait --wait-timeout 180
Get-Content -Raw "$work/accounts.json" |
  docker @compose exec -T drf-web python manage.py shell --no-imports --command 'from seed import main; main()'
$python = '.\tests\.venv\Scripts\python.exe'
$gateway = 'http://127.0.0.1:18080'
$out = "$work/results"
New-Item -ItemType Directory -Force $out | Out-Null

function Select-Drf([string]$orm, [string]$dashboard) {
    $env:TF_LOAD_ORM = $orm
    $env:TF_LOAD_DASHBOARD = $dashboard
    docker @compose up -d --no-build --no-deps --wait --wait-timeout 70 drf-web
}

function Run-Load([string]$case, [string]$label, [int]$users, [int]$seconds = 20, [int]$firstAccount = 0) {
    $env:TF_LOAD_SCENARIO = $case
    $env:TF_LOAD_ACCOUNT_START = "$firstAccount"
    $failureExit = if ($label -eq 'sse-above') { 0 } else { 1 }
    & $python -m locust -f tests/load/locustfile.py --headless --host $gateway -u $users -r $users -t "${seconds}s" `
        --stop-timeout 5 --csv "$out/$label" --csv-full-history --exit-code-on-error $failureExit
}

Select-Drf 'n+1' 'hot'
Run-Load list list-n1 8
Run-Load detail detail-n1 8
Select-Drf optimized hot
Run-Load list list-optimized 8
Run-Load detail detail-optimized 8
Select-Drf optimized cold
Run-Load dashboard dashboard-cold 8 15
Select-Drf optimized hot
Run-Load dashboard dashboard-hot 8 15

# 在隔离项目中清理前次分析缓存，保留鉴权、限流和其他缓存。
docker @compose exec -T redis sh -c 'redis-cli -n 1 --scan --pattern "ticketflow:ai:analysis:*" | xargs -r redis-cli -n 1 UNLINK'
Run-Load analysis analysis-below 2 20 0
Run-Load analysis analysis-above 12 20 2
Run-Load sse sse-below 2 20 14
Run-Load sse sse-above 12 20 16
& $python tests/load/disconnect.py --host $gateway --csv "$out/disconnect.csv"
& $python tests/load/query_probes.py --host $gateway --csv "$out/query-probes.csv"
```

已启动隔离栈并造数时，可单独运行最后一条命令采集 SQL 探针。脚本切换并等待各个 DRF 档位，用同一账号对列表和详情各预热一次，再读取 SQL 计数和响应摘要。看板冷档采两次未命中，热档先预热再采两次命中。整轮校验通过后覆盖目标 CSV，结束时隔离栈处于优化查询、热缓存档位。

SSE 超容量组允许命令退出码为 0，以便保留预期的 `503 UPSTREAM_BUSY` 样本。核对其失败 CSV，其他错误均需单独解释。单独重复 AI 组前，留出 60 秒供该组客服账号的上下文限流窗口过期。
