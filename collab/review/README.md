# 评审清单（Gemini）

只读评审，不修改代码、不提交。对象是 `collab/reports/<任务号>.md` 里写明的分支：

```powershell
git -C F:\Program\ticketflow-ai fetch --all
git -C F:\Program\ticketflow-ai diff main...<分支>
```

先读完成报告、对应任务书（`collab/tasks/`）和
[Phase 1 设计评审](../../backend-drf/docs/plans/ticketflow-phase-1.md)，再看代码。

## 必查项

1. **契约**：请求、响应、状态码（400 / 403 / 404 / 409 / 429 / 503）与设计文档和
   `backend-drf/docs/schema/` 一致；改了响应结构就必须同时改了契约文件。
2. **权限与数据范围**：列表、详情、看板、导出、AI 上下文是否都经过同一个范围约束；
   内部备注、内部日志、受限来源字段会不会泄露给提交人；前端是否只依据后端给出的能力字段显示操作。
3. **并发与一致性**：写操作是否在事务内加锁并校验 `version`；缓存失效是否在提交后执行；
   幂等和限流在 Redis 故障时的行为。
4. **安全**：Markdown 和富文本渲染是否净化；有没有把用户输入拼进 SQL、HTML 或 Redis 脚本；
   有没有硬编码密钥或把敏感信息写进日志。
5. **测试**：新行为有没有守护测试；测试断言的是行为而不是实现细节；报告里声称通过的命令
   是否真的列出了输出。
6. **仓库约定**：对照 `backend-drf/AGENTS.md` 或 `frontend/AGENTS.md`，重点看迁移纪律、
   种子与权限点、行数门禁、i18n、源码中不得出现任务编号。

## 输出格式

写到 `collab/reviews/<任务号>.md`（同一任务复审时追加“第 N 轮”小节，不覆盖历史）：

```markdown
# <任务号> 评审 · 第 1 轮

结论：APPROVE | REQUEST_CHANGES
分支：<分支名> @ <提交短哈希>

## 问题
| 级别 | 位置 | 问题 | 触发场景 |
| --- | --- | --- | --- |
| 阻断 | backend-drf/tickets/views.py:120 | … | 具体输入或状态 → 错误结果 |

## 建议（不阻断）
- …
```

级别：**阻断**（错误行为、安全或数据泄露、契约不一致，必须修）、**一般**（应修但可后续跟进）、
**建议**（风格或可读性）。只要有一条阻断，结论就是 REQUEST_CHANGES。
每条问题都要写清触发场景；无法确认的问题标注“待确认”，不要当作阻断。
